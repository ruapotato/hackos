# 9P

Status: milestone 5, **emulators only** (QEMU's Cortex-M7 and Cortex-M4
machines, Renode's nRF52840 with the Feather image). Nothing here has run
on a board.

9P2000 is how one Hamnix Micro namespace reaches files that somebody else
serves: a program on the same device, or a PC at the other end of the
console's serial line. Three pieces:

| Piece | Where | What it does |
|--|--|--|
| the kernel's client | `fs/p9c.ad`, used by `fs/hvfs.ad` | `mount` attaches a server at a name; `open`, `read`, `write`, `stat`, `create`, `remove`, directory listings and redirections below that name become 9P requests |
| `/srv` | `fs/srv.ad` (the server `#s`) | where a server leaves one end of a connection under a name for others to mount |
| `exportfs` | `user/progs/exportfs.ad` | a 9P server in user space: serves a directory of its own namespace to `/srv`, or to another machine over the console line |
| `srv` | `user/progs/srv.ad` | posts a serial device in `/srv`, so that a 9P server on another machine can be mounted |

On the PC (Python, standard library only): `tools/hm9p.py`, a client for a
device that runs `exportfs /dev/console`; `tools/hm9pd.py`, a server that
gives a device a directory of the PC to mount.

| Direction | Line | Tested on |
|--|--|--|
| a server on the device, mounted on the device | a pipe pair through `/srv` | QEMU M7 and M4, Feather image in Renode |
| the device's tree used from a PC | the console's own serial line (no second UART) | QEMU M7 and M4, Feather image in Renode |
| a PC's directory mounted on the device | a second serial port as a device file (`/dev/eia1`) | QEMU M7 and M4 only: no other board has such a file yet |

## Try it: a server on the device

```
hamsh$ mkdir /tmp/ex
hamsh$ echo one > /tmp/ex/a
hamsh$ exportfs -s ex /tmp/ex &
hamsh$ ls /srv
ex
hamsh$ mount /srv/ex /n/ex
hamsh$ ls /n/ex
a
hamsh$ cat /n/ex/a
one
hamsh$ echo written > /n/ex/new          # Tcreate, Twrite
hamsh$ seq 5 >> /n/ex/new                # a program's output, appended
hamsh$ wc < /n/ex/new
6 6 18
hamsh$ cat /proc/self/ns
...
mount /srv/ex /n/ex
hamsh$ unmount /n/ex
hamsh$ rm /srv/ex                        # exportfs ends: its connection is closed
```

* `exportfs -s NAME [DIR]` makes a socketpair, posts one end as
  `/srv/NAME` and serves `DIR` (default `/`) on the other. What it serves
  is what *it* sees: started inside `ns { bind ... ; exportfs -s x / & }` it
  exports that tailored namespace.
* `mount [-b|-a] /srv/NAME PATH [as LABEL]` is the shell's own command
  (Hamnix's `hamsh`, unmodified): `srv_open(NAME)` then `mount(fd, -1,
  PATH, flag, 0)`. A mount is a namespace entry like a bind: per process,
  inherited or copied the same way, a union member with `-b`/`-a`, shown by
  `/proc/<pid>/ns` as the command that made it, removed by `unmount PATH`
  or `unmount LABEL`.
* The same server can be mounted at several names and in several
  namespaces; they share one connection.
* A server that ends while it is mounted makes every later use fail with
  "9P: the server has gone" (tested by killing it); nothing hangs.
* Hamnix's own demo server works the same way (`p9srv_demo post demo &`,
  `mount /srv/demo /n/demo`, `cat /n/demo/hello`); it is in the QEMU and
  Teensy images, not in the Feather's.

On the Feather nRF52840 the same commands work (Renode). `exportfs` takes a
12 KB block of the program arena there, so beside it and the shell there
is room for small programs (`cat`, `ls`, `echo`, `wc`, `seq`, `cp` of small
files with `cat a > b`). `cp` and a pipeline with `grep` failed there for
lack of memory; `vi` and `sort` need blocks at least as large and were not
tried.

## Try it: the device's files from a PC

The device exports its own tree over the serial line its console is on. No
second UART is needed: `exportfs /dev/console` switches the console into a
transparent *wire* mode, speaks 9P until something arrives that is not 9P,
and gives the console back to the shell. The escape is **four zero bytes**
(a message size of 0, which no 9P message has).

On the PC, with the device at its prompt and nothing else holding the port:

```
$ tools/hm9p.py --tty /dev/ttyUSB0 ls /
$ tools/hm9p.py --tty /dev/ttyUSB0 cat /proc/version
$ tools/hm9p.py --tty /dev/ttyUSB0 write /dev/gpio/blue 1      # Feather: the blue LED
$ tools/hm9p.py --tty /dev/ttyUSB0 cat /dev/gpio/button
$ tools/hm9p.py --tty /dev/ttyUSB0 put notes.txt /tmp/notes.txt -- ls /tmp
$ tools/hm9p.py --tty /dev/ttyUSB0 get /bin/hello hello.elf
```

The tool types `exportfs /dev/console` at the prompt, waits for its line
"exportfs: 9P on the console until four zero bytes arrive", does what was
asked, sends the four zero bytes and waits for "the console is a console
again". `--root DIR` exports a directory instead of `/`; `--cmd` and `--tcp`
talk to an emulator instead of a tty (that is how the tests run it). It can
also be used as a Python module (`hm9p.Session`, `hm9p.Client`).

What is and is not tested:

* **Tested** (`make test`, `make test-m4`: QEMU's UART on stdio; `make
  test-nrf52`: the unchanged Feather image in Renode, its UARTE0 on a TCP
  socket): version and attach, directory reads, a 1000-byte file written in
  256-byte requests and read back, every byte value 0..255 in both
  directions, `/bin/hello` compared with the build's file, create, mkdir,
  remove, an error, switching a GPIO pin from the host, the escape, and the
  shell working afterwards. 16 checks, `tests/9p/host_test.py`.
* **Not tested: a real serial line.** The `--tty` path of the tool
  (termios, raw, 115200) has never been run; neither emulator has a baud
  rate or a finite receive FIFO. Messages over a device are limited to 280
  bytes so that a whole request fits the console's 1024-byte input ring
  below the point (512 bytes) where the Feather would send XOFF into the
  stream; whether its one-byte-at-a-time UARTE receive keeps up with a
  280-byte burst at 115200 baud is exactly what the emulators cannot show.
* While the session runs the shell is waiting for `exportfs`, so nothing
  else prints on the console. A kernel message (a fault report) in that time
  would corrupt the stream; the client then times out.
* Linux's own 9P client (`mount -t 9p -o trans=fd,version=9p2000`) should be
  able to use the same connection through a file descriptor on the tty. Not
  tried.

## Try it: a PC's directory mounted on the device

`mount` takes any descriptor that carries bytes both ways. A serial port
that is a device file can therefore lead to a 9P server on another
machine. `srv DEVICE NAME` posts the device in `/srv` so that the shell's
`mount` can name it:

```
pc$ tools/hm9pd.py --tty /dev/ttyUSB1 ~/shared         # serve a directory

hamsh$ srv /dev/eia1 pc
hamsh$ mount /srv/pc /n/pc
hamsh$ ls /n/pc
hamsh$ cat /n/pc/readme
hamsh$ echo made-on-the-device > /n/pc/note
hamsh$ cp /bin/hello /n/pc/hello ; /n/pc/hello          # a program run from the PC's disk
hamsh$ bind -a /n/pc /bin                               # ... or the PC's directory as more of /bin
hamsh$ unmount /n/pc
```

* **Where this works: the QEMU boards only.** Their third UART is
  `/dev/eia1`; the tests connect it to `hm9pd.py` through a Unix socket
  (QEMU: `-serial stdio -serial null -serial unix:PATH,server=on,wait=off`;
  then `hm9pd.py --unix PATH DIR`). Plain `make run` leaves it unconnected. The
  device file is `drivers/tty/cmsdk_eia.ad`: polled once per tick, no
  interrupt, no ring; good enough for QEMU's model, which holds the sender
  while a byte is unread. **The Feather and the Teensy have no `/dev/eia1`**
  (a UARTE1 or LPUART instance registered with `devtree_add` is what it
  takes; `srv` is left out of the Feather image until then).
* A read from the line gives up after 5 s of silence, so a `mount` of a
  line nobody answers on fails with "9P: the server has gone" after 5 s
  (tested) instead of hanging; the price is that a server must answer each
  request within 5 s.
* `hm9pd.py` serves one directory tree, refuses names that lead outside it,
  and has `--read-only`. Its `--tty` mode has never been run.

## How it works

* **Transport.** `socketpair(…, sv)` (53) gives two descriptors, each
  reading what the other writes (two kernel pipes). `srv_post(name, fd)`
  (275) leaves one end in `/srv`; `srv_open(name)` (276) gives a descriptor
  for it; `mount(srvfd, afd, old, flag, spec)` (258) hands it to the kernel.
* **Connection.** `mount` sends `Tversion` (msize 4120; 1048 on the
  Feather) and `Tattach` (no `Tauth`: `afid` is NOFID, user `hmicro`). A
  connection is a 4 KB message buffer (1 KB on the Feather), a lock and a
  fid bitmap: fid 0 is the root, 1..31 are handed out. Four connections at
  most. One request at a time per connection, tag 1.
* **Names.** A mount is the namespace entry `PATH -> #M<n>`. A lookup below
  it is `Twalk` from the root fid with a new fid (16 names per walk), then
  `Topen`/`Tcreate`/`Tstat`/`Tremove`, and `Tclunk` when the file is closed.
  A directory is listed by reading its stat records.
* **Redirections.** `cmd > /n/x/f` goes through `openchan` like every
  redirection: for a 9P file the channel is an entry of the open-file table
  that the shell binds at the child's `/fd/1`; every `/fd` name it is bound
  at holds a reference and the last one clunks the fid.
* **References.** A connection lives while a namespace entry, an open file
  or an operation in progress refers to it; the last reference closes the
  transport, which is the server's end of file.
* **Interrupts.** A request whose caller is ended (Ctrl-C) while waiting
  leaves its reply on the wire; the next request on that connection reads
  it away first. No `Tflush`.
* **`exportfs`.** Sixteen fids, each a path and (once open) a descriptor;
  requests are mapped to ordinary system calls in its own namespace
  (`stat_p9` gives the stat record ready-made). `Tauth` is refused ("no
  authentication required", as 9P allows), `Twstat` is not supported (`mv`
  across the mount copies and removes).

## Measured (QEMU `mps2-an500`; Feather in Renode where stated)

| | |
|--|--|
| kernel heap per mounted server | one message buffer: 4,120 bytes (Feather: 1,048) |
| static data | 4 connections x 104 bytes; `/srv`: 8 names x 36 bytes |
| `exportfs` as a process | QEMU: 32 KB block (13 KB of buffers, 8 KB stack); Feather: 12 KB block |
| host session over the console (`host_test.py`) | 123 requests in 0.2-0.5 s on QEMU, 125 in about 1.1 s on Renode: emulator speeds, not a line's |

## Differences from Hamnix

* The client is new code (`fs/p9c.ad`, 650 lines). Hamnix's
  `sys/src/9/port/9p_client.ad` (2,500 lines) is built on Hamnix's
  descriptor, pipe and Chan structures and keeps a page cache per
  connection. The wire format and the user-side library (`lib/9p/9p.ad`,
  copied unmodified) are the same.
* `/srv` holds the posted end itself, not a descriptor number of the
  poster: a name stays good after the poster closes its descriptor, until
  `rm /srv/NAME`. `/srv` is listable and its entries removable. A device
  file can be posted as well as a socketpair end (`srv`); Hamnix has no
  such thing because its transports are sockets.
* `mount` closes `srvfd` on success (Hamnix leaves it open; here that would
  use up the shell's sixteen descriptors).
* No `Tauth` (Hamnix can attach with an auth fid), no `Tflush`, no
  `Twstat`, no caching, one tree per server (`spec` is ignored).
* `unmount /srv/NAME PATH` finds the mount by the name it was mounted from.
